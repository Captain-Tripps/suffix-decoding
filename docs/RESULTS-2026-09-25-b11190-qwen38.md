# Qwen3.8 Q8 speculative drafter check on b11190-f16 (2026-09-25)

Zeus, dual Arc Pro B70, Bartowski Qwen3.8-27B Q8_0. Controlled A/B on the **same** `b11190-f16` SYCL binary. Production Qwen flags were held constant: 131072 context, q4_0 KV, batch 2048/512, 8 CPU threads, `-ngl 99`, MTP draft max 3. Only `--spec-type draft-mtp` versus `--spec-type ngram-mod,draft-mtp` changed. Temperature 0, seed 42, one warmup call per process. The test script is `scripts/bench-current-qwen38.ps1`.

| Prompt | MTP tok/s | ngram + MTP tok/s | Accepted drafts, ngram + MTP | Wall time MTP -> ngram |
|---|---:|---:|---:|---:|
| JSON first | 44.1 | 44.0 | 18/18 | 1.29 -> 1.29 s |
| JSON repeat | 44.0 | 44.1 | 18/18 | 0.66 -> 0.66 s |
| JSON variant | 44.2 | 44.1 | 18/18 | 1.22 -> 1.24 s |
| Code first | 44.8 | 44.8 | 100/102 | 3.65 -> 3.67 s |

| Code repeat 2 | 44.7 | **103.0** | 131/131 | 3.09 -> **1.42 s** |
| Refactor | 38.9 | 38.8 | 154/193 | 6.27 -> 6.28 s |

The warm exact-code repeats were **2.18x and 2.30x faster in decode**. This reproduces the August `ngram-mod` result on the newer binary. Cold code, short JSON, and the refactor prompt did not materially change. The refactor response hit the 220-token output cap in both arms; this row measures speed, not answer quality. These are short synthetic prompts and a single pass, so they establish the mechanism rather than a sustained gain for actual agent sessions.

The older suffix port was **not** run here: it is on the August branch and binary, so comparing it with `b11190-f16` would conflate speculative method with llama.cpp and SYCL version. August's same-binary suffix A/B found regressions on varied JSON and refactoring and a lower warm-code peak than ngram. A representative agent trace with repeated tool outputs/code edits and fresh prompts remains the useful gate for a production decision.

## Isolated suffix build attempt

The two August suffix commits applied cleanly to an archive of the local September 15 `llama.cpp-b70fix` source (`f4f929f`). Compilation found one API change: the `common_speculative_impl` base constructor now requires `n_max`. Passing `spec_params.suffix.n_max` fixed it. A full oneAPI 2026 SYCL `llama-server` build then succeeded, and `--help` exposes the suffix flags. The isolated executable is in `%TEMP%\llama-suffix-b11190-eval\stage\llama-server.exe`; neither production source nor runtime was changed. This source is newer than August's port but older than the production `b11190-f16` binary, which reports commit `fcc8915`.

The first same-binary attempt stopped when GPT-OSS received new production traffic during the unload handoff. The run completed on September 26 after the GPUs became idle again.

## September 26 same-binary comparison

All configurations below use the **same patched `f4f929f` binary**, same Qwen Q8 model and production-equivalent flags. Each configuration starts a fresh server and runs the same seven prompts in order. Numbers are generation tokens/second, one pass per prompt.

| Prompt | MTP | ngram + MTP | suffix + MTP default | suffix min match 16 | suffix min match 16, draft max 8 |
|---|---:|---:|---:|---:|---:|
| JSON first | 44.2 | 41.2 | 12.4 | 15.6 | 24.9 |
| JSON repeat | 44.2 | 43.9 | 12.8 | 12.8 | 14.1 |
| JSON variant | 44.1 | 43.8 | 10.1 | 12.0 | 18.2 |
| Code first | 44.6 | 44.7 | 42.9 | 44.4 | 44.4 |
| Code repeat 1 | 44.7 | **98.4** | 55.3 | 55.4 | 16.1 |
| Code repeat 2 | 44.7 | **103.4** | 43.3 | 44.6 | 16.1 |
| Refactor | 38.9 | 38.9 | 30.0 | 33.7 | 36.7 |

The newer source did **not** rescue the suffix port. Default suffix reduced JSON decode from about 44 to 10-13 t/s and refactor from 39 to 30 t/s. Its best warm-code result was 55 t/s, well below ngram's 98-103 t/s. Raising the minimum match from 5 to 16 was insufficient. Capping suffix drafts at 8 tokens reduced some JSON cost, but warm repeated code fell to 16 t/s. That run accepted 116 of 120 drafted tokens on each repeat, so acceptance alone does not guarantee speed; short verification cycles and drafter overhead appear to dominate. This is an inference from the timings and draft counts, not a profiler result.

These are short synthetic prompts, and the refactor hit the 220-token limit. We have not measured a real agent trace or output-quality parity. The result is strong enough **not to promote this suffix port to production**. `ngram-mod,draft-mtp` remains the practical choice for exact repeated code, while plain MTP is already as fast on the nonrepeating prompts in this sample.
